# 编排层原型设计计划

日期：2026-09-23。状态：设计草案，尚未实施。整体边界见[架构讨论纪要](../architecture/overview.md)，模型调用契约见 [AI 请求层设计计划](ai-request-layer.md)。

## 已确定的方向

- 先用 LangGraph 验证一轮文字对话的编排，重点是当前 Context 的构造、过往会话记忆导入和设定卡装配。
- 用 Langfuse 观察图节点和模型调用；后续 Rust 实现沿用可迁移的追踪语义。
- AI 请求层由另一位协作者处理。编排层只依赖其统一请求与响应契约，不接管服务商适配。
- 原型用于验证流程和数据边界，不表示 LangGraph 已成为 Rust 核心运行时的一部分。

## 原型范围

一轮用户消息触发一次编排：读取固定版本的输入和数据快照，装配 Context，调用一次 `send_messages`，记录结果及构造依据。先覆盖纯文本；工具循环、主动互动和生活状态调度留待后续阶段。

建议图路径：

```text
本轮输入与版本快照
  → 读取设定卡、当前会话和候选记忆
  → 归一化、冲突检查与预算选择
  → 渲染统一请求
  → AI 请求层 send_messages
  → 保存本轮结果与构造记录
```

| 阶段 | 输入与产出 | 需要验证的边界 |
| --- | --- | --- |
| 快照 | 本轮消息、会话版本、设定卡版本、预算配置 | 重试必须绑定同一版本；新消息到达后的处理策略待定 |
| 读取 | 当前会话、原始历史、已提炼记忆与来源 | 历史原文与衍生记忆分开；缺失来源可识别 |
| 装配 | 有序片段及取舍记录 | 角色设定、明确纠正、当前输入和旧记忆的优先关系可解释 |
| 请求 | 请求层统一消息和工具契约 | 不传服务商原生 JSON，不在编排层处理鉴权与传输 |
| 结果 | 助手消息、结束原因、可用用量、关联版本 | 仅完整成功结果进入会话；失败及取消不写入衍生记忆 |

### 过往会话导入

导入是独立于每轮检索的准备步骤。先保留原始消息及稳定来源标识、时间、角色、会话归属和顺序，再提炼摘要或候选事实。重复导入应得到同一批结果；发现错误时能依据来源更正或删除衍生记忆。原始记录的格式、存储方案和提炼算法尚待确定，原型可先使用少量去标识化样本。

每轮只读取与本轮相关的候选项和必要的近期原文，不把全部历史塞进 Context。候选记忆至少带来源、时间、状态和可信度或确认方式，便于处理过期、矛盾和用户纠正。

### 设定卡与 Context

设定卡建议分开保存稳定身份、表达风格、互动边界和版本。装配时记录采用的版本；用户明确更新的偏好进入对应数据层，不静默改写设定卡。旧记忆与设定卡或用户当前明确纠正冲突时，标记并排除冲突项，具体优先级需由产品负责人确认。

Context 构造先预留模型输出空间，再按预算选择角色设定、当前输入、当前会话与候选记忆。保留每个片段的来源、预算占用和纳入／舍弃原因。预算值与请求层模型配置保持一致；超额时明确缩减或报错，不静默截断关键设定。渲染后的统一请求是可检查的原型产物。

### 状态、恢复与观测

图状态只保存本轮执行所需的快照标识、阶段结果和错误；原始会话、长期记忆与设定卡由各自的数据源负责。LangGraph checkpoint 用于原型内的步骤恢复，不作为长期记忆库。首次原型可用临时 checkpoint；跨进程恢复、取消和重复提交在接入持久存储前再明确。

一轮编排对应一个 Langfuse trace。节点分别记录读取、选择、装配、请求和结果的耗时、版本、数量及取舍摘要；模型调用记录可用的 token 用量和结束原因。原型只用去标识化样本；回调可能采集输入输出，接入真实数据前须验证脱敏和过滤配置，并决定原文采样与保留期限。密钥不得进入日志或 trace。观测上报失败不应改变本轮结果，但应可在本地诊断。

Langfuse 官方提供 [LangGraph 回调集成](https://langfuse.com/integrations/frameworks/langgraph)；Python 原型可借此追踪图运行。Langfuse 也提供 [OpenTelemetry 接收端](https://langfuse.com/integrations/native/opentelemetry)，Rust 阶段可用 OpenTelemetry 输出 trace。此处的“兼容”指观测数据可接入，不承诺 LangGraph 图代码能直接迁入 Rust。LangGraph 的 [checkpoint 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)与产品长期记忆应保持不同职责。

## 实施顺序与验收

1. 与 AI 请求层协作者确认统一消息、完成事件、取消、错误和预算信息，记录在[编排协作文档](orchestration-collaboration.md)。
2. 由人实现可在本地运行的 LangGraph 最小图，先用固定响应完成设定卡、历史和记忆装配，再接入实际请求层。
3. 用少量有冲突、过期、重复导入和预算不足的样本检查装配结果与来源记录。
4. 接入 Langfuse，核对一轮 trace 的节点关系、关联版本、错误路径和敏感内容过滤。
5. 根据原型结果决定 Rust 内移植编排逻辑，或保留独立 Python 组件；确定存储和跨进程契约后再扩展工具循环。

验收以可复现样本为准：同一输入快照得到相同的选材及请求；重复导入不产生重复记忆；冲突和舍弃原因可见；调用成功、失败、取消不会写错会话版本；一轮 trace 能串起编排与请求。具体类型、存储和接口形式仍待实现者确认。
