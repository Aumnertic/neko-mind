# AI 请求层设计计划

日期：2026-09-23。状态：设计草案，未实施。整体背景见 [架构讨论纪要](../architecture/overview.md)。

已确认：统一 `send_messages` 入口、启动时加载配置、内部兼容 API、与上下文解耦、由上层处理回复和工具调用。下文具体类型、目录及流式契约仍是建议。

## 目录建议

先在当前 crate 中建立 `ai` 模块；文件按职责划分，小文件可以合并。按实际接入协议增加适配器，不预建空实现。

```text
src/ai/
├── mod.rs                 # 公共导出
├── client.rs              # 统一调用入口
├── config.rs              # 配置、默认值和校验
├── error.rs               # 统一错误
├── protocol/
│   ├── mod.rs
│   ├── message.rs         # 消息与内容块
│   ├── request.rs         # 单次请求
│   ├── response.rs        # 事件、完整响应和用量
│   └── tool.rs            # 工具定义、调用和结果
├── providers/
│   ├── mod.rs             # 私有适配器选择
│   └── openai_chat.rs     # 协议示例，首个协议待定
└── transport/
    ├── mod.rs
    ├── http.rs            # 单次 HTTP 传输
    └── sse.rs             # 通用事件分帧
```

上下文依赖统一请求协议，运行时调用 AI 客户端；AI 层不反向依赖上下文、记忆或人格模块。`providers` 和 `transport` 保持私有。

## 初始化与调用

建议客户端命名为 `AiClient`。初始化时校验配置、选择协议并创建可复用的 HTTP 客户端，业务方法只有 `send_messages`。

| 来源 | 内容 |
| --- | --- |
| 启动配置 | 协议、地址、凭据、模型、默认生成参数、超时策略 |
| 单次请求 `AiRequest` | `messages`、`tools`、`tool_choice` |

每次调用不读配置文件、不创建连接池、不保存聊天历史。聊天和记忆提取如需不同模型，可用不同配置构造客户端。

上下文预算与客户端输出上限来自一致配置。配置格式、热更新、单次参数覆盖尚未确定；初版建议使用不可变配置。

## 消息与工具

统一协议使用明确类型，避免用字符串 role 和任意字符串映射表达所有内容。

| 类型 | 关键语义 |
| --- | --- |
| 系统／用户消息 | 指令与用户输入；内容块按需支持多模态透传 |
| 助手消息 | 有序内容块，可同时包含文字和多个工具调用 |
| 工具定义 | 名称、说明、参数 schema，独立于消息历史 |
| 工具调用 | 调用 ID、名称、结构化 JSON 参数 |
| 工具结果 | 对应调用 ID、结果内容和执行错误标记 |

`tool_choice` 是请求策略，`tool_calls` 是模型实际返回的调用。助手消息应能直接放回历史，工具结果按调用 ID 匹配，不能只按工具名。

一次 `send_messages` 只完成一次模型调用。运行时检查和执行工具、追加结果、决定是否继续调用及何时终止。

## 流式接口建议

建议返回 `AiStream`，内部事件为 `AiEvent`，最终结果为 `AiResponse`。实时聊天消费增量，后台任务消费到最终结果，入口保持一致。

| 事件 | 内容与用途 |
| --- | --- |
| 文本增量 | 内容块索引和新增文字，供即时展示 |
| 完成 | 完整助手消息、结束原因和可用的用量，供保存与工具处理 |

- 工具参数碎片内部组装，上层在完成后处理完整调用。
- 成功恰好产生一个完成事件；错误后终止，异常断流不能伪造完成。
- 完整响应包含已展示的文字，界面不能重复追加。
- 区分正常结束、工具调用和输出上限；未知用量不记为零。
- 不完整或损坏的工具参数不能作为可执行调用返回，具体表示待定。
- 非流式后端可直接产生完成事件，沿用相同入口。

返回形式和事件契约需在实现前确认。

## 适配器与抽象

按协议组织适配器，例如 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages；兼容同一协议的服务商尽量复用实现。

适配器负责请求映射、协议鉴权、事件解释、工具聚合及结果归一化。服务商专用序列化结构留在内部，不让上下文模块填写原生 JSON。

不支持的能力明确报错，不能静默忽略强制工具调用等要求。未来若协议要求签名或续接标识，应内部保留并随历史回传，具体方案按需设计。

| 模式 | 用途 |
| --- | --- |
| 门面 | `AiClient` 集中公开入口 |
| 适配器 | 转换并隔离协议差异 |
| 策略 | 根据配置选择执行路径 |

初期可用私有枚举分发，外部注入需求明确后再考虑 trait；暂不引入插件注册表、复杂 Builder 或通用中间件链。

## 传输、错误与取消

HTTP 层负责一次传输，SSE 层只做分帧，适配器解释事件。网络读取块不等于完整事件，需要处理任意拆分和合并。

建议错误分类：配置、请求参数、不支持能力、鉴权、限流、网络／超时、服务端、响应协议。保留必要请求 ID 和错误来源，日志不泄露凭据。

重试由客户端结合输出阶段决定。输出前可按明确策略有限重试；远端是否已执行有时仍不确定。输出后建议终止并交上层处理，避免重试重复文字或工具调用。默认策略待定。

建议丢弃流即取消本地读取；若使用后台任务，消费者退出必须能终止它。取消不保证远端立即停止计算或计费。并发调用各自持有组装状态，不使用全局对话锁。

## 实施与验证

1. 确认首个协议、配置格式、请求范围和返回契约。
2. 由人实现统一协议、初始化和首个适配器。
3. 验证流解析、工具回传、错误和取消，再接入上下文与运行时。

测试重点：文本与多个工具混合返回、调用 ID 回传、任意字节分块、多字节文字、异常断流、截断参数、缺失用量、能力不支持、重试重复及取消清理。

固定响应样本验证协议和边界，真实 API 联调确认兼容性。Agent 可以编写测试和辅助脚本；核心实现与发现的产品代码问题由人处理，见 [AGENTS.md](../../AGENTS.md)。
