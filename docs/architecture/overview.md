# 架构讨论纪要

日期：2026-09-23。仓库处于早期原型阶段；本文记录共识和候选方案，不代表功能已实现。

## 已确认的方向

- neko-mind 是 AI 女友项目 neko 的独立核心运行时，主要使用 Rust。
- 主打文字聊天，多模态依赖模型及配置，不建设独立媒体处理系统。
- AI 请求、上下文构造、记忆管理是基础；上下文管理是聊天效果的核心。
- 还需支持角色与关系状态、对话编排、行为调度和主动互动，具体实现待定。
- 初期首要目标是行为合理性。学习和优化算法需要明确目标及足量数据，不作为首版前提。

## 职责边界

| 模块 | 负责什么 |
| --- | --- |
| AI 请求 | 通用模型调用、API 适配、流式输出和错误处理 |
| 上下文 | 选择角色、状态、历史与记忆，处理冲突并分配 token 预算 |
| 记忆 | 提取、检索、更新、纠错、遗忘和来源追溯 |
| 角色与关系 | 稳定设定、称呼偏好、互动约定与短期状态 |
| 对话编排 | 消息合并、模型调用、工具循环、打断和结果提交 |
| 行为调度 | 推进生活与通信状态，决定何时回应或产生主动互动意图 |

账号、界面、通知投递等由外层应用承担。neko-mind 的嵌入形式，包括是否提供 Python 绑定，尚未确定。

## 请求层与上下文解耦

请求层的业务入口只有 `send_messages`。模型、参数、API 等配置在启动时加载到内存，兼容处理封装在内部。

上下文模块产出统一请求，运行时调用客户端并分别处理正常回复和工具调用。请求层不理解女友人格，不执行工具，也不维护聊天历史。

一次调用只完成一次模型请求；工具执行及携带结果的后续调用由运行时推进。具体方案见 [AI 请求层设计计划](../plans/ai-request-layer.md)。

## 上下文和记忆的建议

上下文构造分为：准备本轮快照与候选记忆、选择信息并分配预算、渲染统一请求。预算信息与模型配置保持一致，但不需要暴露 API 凭据或原生格式。

构造过程尽量只读。保存内部构造记录，说明采用了哪些记忆、舍弃了哪些历史及预算分配，便于解释聊天效果。

信息按来源与稳定性拆分：

- 角色设定：身份、表达风格等，明确配置，避免每轮随意改写。
- 用户事实与偏好：支持纠正和过期，不将一次情绪永久写成人格画像。
- 共同经历与关系约定：记录“我们发生过什么”和明确的互动偏好。
- 当前话题与未完成事项：关联时间、状态和完成条件。

原始聊天记录与提炼的记忆分开，记忆能追溯到原文。明确偏好和约定可结构化保存，共同经历可结合摘要与语义检索，存储技术待定。

## 生活感与对话生命周期

候选设计是两条相互影响的过程：

- 生活：开始活动 → 持续 → 被打断或结束 → 下一项活动。
- 通信：消息到达 → 注意到 → 阅读 → 决定回应 → 组织并发送。

真实感首先来自连续状态和可理解的原因。每次来消息都重新随机抽取生活状态，容易前后矛盾；回复等待时间应有活动或注意力上的依据。

最小状态可从以下范围验证，字段尚未定稿：

| 类别 | 候选信息 |
| --- | --- |
| 行为倾向 | 作息、规律性、查看消息倾向、可打断程度 |
| 生活状态 | 当前活动、开始时间、预计持续时间、注意力 |
| 通信状态 | 未读、已读未回复、交流活跃状态、下次检查时间 |

人格描述与行为参数分开，用预设加少量覆盖降低配置负担。例如“内向”不必然意味着回复慢。

算法可先研究事件驱动的半马尔可夫模型：转移受当前状态及其持续时间影响。随机性落在当日节奏和活动时长等层面，计划因相关事件而调整。

环境来自固定背景、当日计划和已发生事件；对话中的时间承诺也需进入调度。大模型可辅助提出计划，运行时保证一致性。贝叶斯可用于估计未知参数，随机抽样本身不等于贝叶斯推断。

## 提交与主动互动

建议流程：事件到达 → 更新状态并判断是否回应 → 读取最新快照 → 构造上下文 → 模型调用与工具循环 → 提交结果 → 更新记忆和状态。

模型生成、用户看到、最终保留的内容可能不同。记忆更新应关联明确的事件或对话版本，避免重试、重新生成和过期任务造成重复或错误写入。

行为调度输出下次唤醒时间及互动意图，外层负责唤醒和实际发送。首版可先验证用户消息触发的交流。

## 待定与下一步

- 明确连续消息合并、取消、重新生成、投递与提交的语义。
- 确定状态字段、时间推进方式、人格配置和承诺记录方式。
- 选择记忆存储、版本控制及工具循环策略。
- 先验证“正在忙”和“正在看手机”两个场景，再看打断、连续交流、回到原活动是否自然。
